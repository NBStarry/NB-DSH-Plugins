# Feishu tasks / 飞书任务

Native DSH sidebar entry and keyed main panel. The UI and `feishu_tasks_list` agent tool share a read-only Host operation. Does not replace the conversation panel, modify Feishu tasks, or switch the CLI default account.

## Features

- Defaults to all configured CLI profiles. Account dropdown and collapsible account-group labels include the profile alias, so identical display names stay distinguishable.
- Todo/completed/all filters, local title search, ascending/descending due-date sorting (undated tasks last), overdue labels, manual refresh and safe HTTPS Feishu links.
- Independent account errors retain other accounts’ successful tasks. Incomplete-result notice and per-account safe errors; every-account failure is explicitly an error, never “no tasks”.
- Host theme tokens, reactive English/Chinese locale, keyboard-accessible controls, loading/empty/error states and pagination warnings.
- No background polling, standalone page, iframe, extra server, npm dependencies or installation scripts.

## Runtime and account contract

Requires DSH Web services `webServer`, `connection`, `tools`, Client slots and locale, and the local Feishu CLI used by `data.js`. Never put tokens in this package or patch.

The CLI account directory comes only from the read-only `lark-cli profile list` command, a bare JSON array. Only profile name, public display label, active and effective flags are retained; app IDs, raw errors and credential fields are not returned. Profiles remain selectable even when their token status reports an error. No credential/config files are read. Empty directories and malformed responses are explicit errors; there is no implicit default-account fallback masking directory failures. A single listed profile works without extra setup; the underlying single-account loader also remains compatible with calls that omit `profile`.

Tasks use the same native command as v1.0 with explicit `--profile <discovered-name>` appended as separate argv values. The selected profile must belong to the current account directory. `profile use` is never called. At most two accounts run concurrently; each has independent pagination, a 20-page limit, 60-second task-read budget, 15-second subprocess timeout and account-local GUID deduplication. Aggregation and React keys use `[accountId, guid]`, not a display name. Profile listing has a 15-second bound and rejects oversized/malformed directories rather than silently truncating them.

The authenticated GET resource is `/api/feishu-tasks?status=todo|done|all&account=all|<profile-id>`; both parameters are optional and default to `todo` and `all`. `feishu_tasks_list` accepts matching optional `status` and `account` parameters. Its default read returns the public `accounts` directory for account-ID discovery. `all` is reserved for aggregation; a CLI profile literally named `all` cannot currently be selected individually. Responses include tasks with `accountId`/`accountLabel`, per-account `state` (`ok`, `error`, `unselected`), safe error codes, `partial`, `allFailed`, `truncated` and `fetchedAt`. Account failures do not clear another account’s successful tasks; cancellation aborts the entire read and drains active workers.

The resource calls `connection.admit` for ordinary HTTP requests and requires an owner principal. Trusted internal `readResource` calls use their supplied peer and still require owner authority. JSON is `no-store`; HEAD does not invoke the CLI. Only safe error codes cross HTTP; command output is not exposed. The agent tool and endpoint call the same validated service method.

Client fetches are cancelled on status/account change or unmount; late responses are discarded. Dates use the active locale and browser timezone; date-only deadlines become overdue after their local calendar date.

## Preload other filters on opening (v1.5.0, Client only)

Opening the panel starts its normal foreground read, then one background `status=all&account=all` read after the active foreground settles. Fast filter replacements retain foreground priority before that preload starts, so it does not compete with the initial Host read. The foreground never waits for preloading. The existing safe cache derives todo/completed and individual-account views, including parent context and recomputed counts; it does not request every filter combination. Switching to all/all while preloading shares that in-flight request. Later foreground visits retain the existing SWR revalidation behavior. A background completion notifies the current view; ordinary background failures leave foreground data alone. All-account failures are not used to derive an empty filtered view, and partial supersets retain matching cached successful accounts where available.

The shared preload survives filter changes, but panel unmount aborts it and all remaining reads. A foreground filter change cancels its non-shared read; late/aborted responses cannot commit. A 401/403 from either foreground or background clears the entire cache and account list, notifies the visible panel, aborts other reads, and invalidates their write epochs. No browser storage, timers, extra server, Host changes, task writes or account switching are added. Host pagination remains bounded (20 pages/account); truncated, partial and parent-context indicators remain meaningful, so preloading is not a promise of a complete remote archive.

## Cached display with background refresh (v1.4.0, historical Client behavior)

Switching filters shows cached tasks immediately while a background request refreshes them; a small “refreshing” notice appears and the fresh result replaces the cached one. The cache is in page memory only: it survives closing and reopening the panel, but is never written to browser storage and is lost when the browser page is refreshed or the plugin is disposed. It holds at most 12 entries for 10 minutes each, keyed exactly by `[status, account]`. A filter not yet visited and not derivable from a cached superset (for example the first switch from To do to Completed) still loads normally.

A view is shown from cache only when it is the exact entry or a true superset: a single account from the same status’s all-accounts entry (only if that account was read successfully), or To do / Completed from an “All tasks” entry (tasks excluded by status stay as parent context so hierarchies remain intact, and counts are recomputed). To do is never guessed as Completed, a single account is never shown as all accounts, and another filter’s data is never displayed: the view key is read synchronously during rendering. No extra reads or prefetching are added; a filter with no exact or superset entry loads as before. When several cached entries can serve a view, the one whose selected accounts were read most recently wins (for all accounts, the oldest of their read times counts; stale accounts keep their original read time), with the exact entry preferred on ties, so a late-stored older superset never replaces newer data.

Refreshes never clear cached data. If a refresh fails, the cached tasks stay visible with a notice giving their original fetch time and the error. If some accounts fail, successful accounts are replaced and each failed account keeps its previous tasks (no older than 10 minutes), marked stale with its error, so a failure never turns earlier results into an empty list. A 401/403 response clears the whole cache and account list; a cache epoch prevents requests started earlier from writing data back afterwards. Cancelled requests and older late responses cannot overwrite current or newer data. Search and sort remain local. Host `index.js`/`data.js` are unchanged, as are the hierarchy and v1.3.1 layout.

All **61 tests** and syntax checks pass, including 14 pure cache tests (miss, hit, superset derivation, cross-account isolation, failed-account exclusion, parent context, freshness ordering across keys including late older supersets and stale-merged accounts, late-write rejection, auth clear with epoch, TTL/bound eviction, partial and total refresh failure). ## Compact accounts and strict parent context (v1.3.0)

Account headers/dropdowns use a short alias without repeating the person’s name (the v1.3.0 neutral user SVG was removed in v1.3.1). An effective generated `cli_*` profile is “Default account”; other generated profiles use a short distinguishing suffix, while custom aliases remain intact. The full account label stays in tooltips/accessibility labels and the agent response. Each group shows one root/container count, with loaded-item detail in its tooltip.

Every task with a parent nests under that parent. Only missing parent GUIDs are fetched using the verified read-only `task tasks get --as user --format json --params {task_guid,user_id_type} --profile <discovered-id>` command; returned GUIDs must match requests. Each account gets at most 20 ancestor requests, eight fetched ancestry levels, a 20-second ancestor-phase budget and a 10-second maximum per get. Ancestors run serially inside the existing two-account workers, so total subprocess concurrency remains at most two. Shared parent GUIDs are deduplicated within an account and never across accounts.

Additional parents are returned separately in `contextTasks` with `contextOnly: true`. They do not change the filtered `tasks`, account `count` or loaded-item totals. Failure, limits or unreadable ancestors produce an explicit expandable parent placeholder and `contextPartial` warning, preserving every child. Self/cycle references are placed under an explicit hierarchy-anomaly container, not disguised as normal roots. There are no standalone orphan child roots. All child branches start collapsed; arrows toggle real loaded children, and search temporarily reveals matching ancestor paths. No task mutation or default-account change occurs.

The v1.2 behavior below is historical and is superseded where it treated orphans as independent roots or used verbose account headers.

## Screenshot-aligned grouped list (v1.2.0, historical)

The existing native panel now uses a lightweight task-title / due-date table, account-group text avatars and counts, thin dividers, read-only status circles, single-line task titles linking to Feishu, and a fixed right column with short dates and red overdue labels. Group collapse and loaded-child expansion are view-only; status circles cannot mark tasks complete. No simulated web page or extra server is used.

The existing task list supplies optional `parent_task_guid`, `subtask_count` and `reminders`; these normalize to `parentTaskGuid` (null when absent), `subtaskCount` (null when unknown, never invented zero), and `hasReminder` (only a nonempty real `reminders` array). A due date alone never generates a bell. There are no additional child-list requests or status-semantic changes.

Parents are linked only within the same account and already-loaded result. Children nest only when their parent exists; missing parents remain visible roots. Cycle edges are broken without dropping tasks. Group counts show **top-level / loaded items**, so a flat list is not mistaken for a hierarchy with the same number of top-level tasks. No fixed task count is assumed. Sorting applies to roots and siblings; child-title search retains ancestor paths and automatically reveals those paths. An arrow is shown only for actual locally loaded children and is operable outside search. Unknown/missing child rows are not fetched; a real total may be shown as “N subtasks” with a tooltip explaining the current-filter subset. No completed/total progress is inferred from a todo-only list.
